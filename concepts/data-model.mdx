The Cinema Backend API revolves around five entities that together model the full lifecycle of a cinema booking. Understanding their fields and relationships will help you build correct request payloads and interpret responses confidently.

All data is stored in plain JavaScript arrays that are initialised empty when the server starts. **There is no persistent storage** — every entity, including its UUID, is lost when the Node.js process stops or restarts.

## Entities

### Movie (`pelicula`)

A movie represents a film that can be scheduled for screening. Movies are the top of the resource hierarchy; they are referenced by show functions.

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | UUID (string) | Server-generated | Unique identifier. Generated by the server via `uuidv4()`. Do not send on create. |
| `titulo` | string | ✅ Yes | The title of the film (e.g. `"Inception"`). |
| `genero` | string | ✅ Yes | Genre or category (e.g. `"Sci-Fi"`, `"Drama"`). |
| `duracion` | number | ✅ Yes | Running time in minutes (e.g. `148`). |

---

### Screening Room (`sala`)

A screening room is a physical auditorium with a fixed maximum capacity. Rooms are referenced by show functions.

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | UUID (string) | Server-generated | Unique identifier. Generated by the server. Do not send on create. |
| `nombre` | string | ✅ Yes | Room name or label (e.g. `"Sala 1"`, `"IMAX"`). |
| `capacidad` | number | ✅ Yes | Maximum number of seats in the room (e.g. `120`). |

---

### Show Function (`funcion`)

A show function schedules a specific movie in a specific screening room at a given date and time. It acts as the central junction in the data model, linking movies and rooms.

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | UUID (string) | Server-generated | Unique identifier. Generated by the server. Do not send on create. |
| `peliculaId` | UUID (string) | ✅ Yes | References an existing `pelicula` by its `id`. |
| `salaId` | UUID (string) | ✅ Yes | References an existing `sala` by its `id`. |
| `horario` | string | ✅ Yes | Date/time of the showing (e.g. `"2025-08-15T20:00:00"`). The API accepts any parseable date string. |

---

### Ticket (`ticket`)

A ticket represents a specific seat assignment for a given show function, with an associated price. Tickets are referenced by reservations.

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | UUID (string) | Server-generated | Unique identifier. Generated by the server. Do not send on create. |
| `funcionId` | UUID (string) | ✅ Yes | References an existing `funcion` by its `id`. |
| `asiento` | string | ✅ Yes | Seat identifier (e.g. `"A12"`, `"F07"`). |
| `precio` | number | ✅ Yes | Ticket price in the application's currency (e.g. `9.99`). |

---

### Reservation (`reservacion`)

A reservation links a named customer to a specific ticket, confirming their booking for a particular seat and function.

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | UUID (string) | Server-generated | Unique identifier. Generated by the server. Do not send on create. |
| `cliente` | string | ✅ Yes | Customer name or identifier (e.g. `"Jane Smith"`). |
| `ticketId` | UUID (string) | ✅ Yes | References an existing `ticket` by its `id`. |
| `fecha` | string | ✅ Yes | Date the reservation was made (e.g. `"2025-08-10"`). The API accepts any parseable date string. |

---

## Entity Relationships

The five entities form a linear chain of dependencies, from movies and rooms down to reservations:

```
Pelicula ──┐
           ├──▶ Funcion ──▶ Ticket ──▶ Reservacion
Sala    ───┘
```

In plain language:

- A **Funcion** joins one **Pelicula** and one **Sala** for a scheduled screening.
- A **Ticket** belongs to one **Funcion** and represents one seat at that screening.
- A **Reservacion** belongs to one **Ticket** and records which customer holds that seat.

Because the API does not enforce referential integrity at the database level (all data is in-memory arrays), it is the client's responsibility to pass valid UUIDs when creating dependent resources. The API will accept any non-empty string for foreign-key fields without verifying that the referenced entity exists.

## ID Rules

<Warning>
**Never include an `id` field in a create (`POST`) request body.** The server calls `uuidv4()` and assigns the `id` itself before pushing the new record into the in-memory array. Any `id` you send will be silently overwritten by the generated UUID.
</Warning>

When updating a resource (`PUT`), the `id` is passed as a URL path parameter (e.g. `PUT /peliculas/update/:id`), not in the request body.

## In-Memory Persistence

<Note>
All data lives only in process memory. There is no file system persistence, no database, and no cache layer. **Restarting the server wipes every record across all five resources.** Plan your testing workflows accordingly.
</Note>
